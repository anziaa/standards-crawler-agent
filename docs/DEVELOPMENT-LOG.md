## 修复与优化记录

以《电梯用钢丝绳》为样例做端到端回归时发现并修复了以下问题。

### 1. `click_view_original` 会直接崩溃

`download` 节点的条件边没有注册 `observe` 分支，而 `after_download()` 在“跳转后需要重新观察”时会返回 `observe`，导致 `KeyError: 'observe'` 中断整张图。现已补上该分支，并让 `click_view_original`、`follow_attachment_page` 在地址发生变化时统一回到 `observe` 重新观察。

同时为该分支加上 `attempts < max_attempts` 约束：此前“跳转 → 重新观察”不受次数限制，一旦模型反复选择跳转，流程会一直转到 LangGraph 的递归上限才结束。现在循环次数由 `AgentConfig.max_page_attempts` 严格控制。

### 2. 生命周期判定把现行标准误判为废止

国家标准详情页会把“标准状态：现行”与“上次复审 / 废止”“代替了以下标准 GB/T 8903-2018”混排在同一段文本里。原判定只看关键词共现，于是把 GB 8903-2024 判成 `ambiguous` 并拒绝下载。现在优先采信指向自身的状态表述（`现行`、`现行有效`、`未废止` 等），只有出现“已废止 / 已作废 / 本标准废止”这类自我废止表述时才判定为废止。

### 3. 官方全文页被内容农场挤出候选

`openstd.samr.gov.cn` 的全文页标题只写“国家标准|GB 8903-2024”，不含中文标准名称，导致按字面 token 计算的页面分数极低而被裁掉。现在：

- 浏览器搜索会同时抽取结果摘要，参与相关性打分；
- 官方标准平台（`openstd.samr.gov.cn`、`std.samr.gov.cn`、`sac.gov.cn` 等）与标准详情页路径（`newGbInfo`、`gbDetailed`、`hcno=`）获得加成；
- 文库、道客巴巴、百科等内容站降权；
- 请求里没有标准编号时，优先较新版本的年份。

### 4. 性能优化

- **浏览器实例复用**：`PlaywrightBrowser` 与 `BrowserSearch` 现在各保持一个长期存活的 Chromium 实例，不再每个查询、每次观察/动作都冷启动一次；`graph.run()` 在 `finally` 中显式回收，避免残留进程。实测搜索 3 个查询从 5.7s 降到 3.7s，观察 2 个页面从 4.1s 降到 3.4s。
- **观察结果剪枝**：链接按“是否可能是目标文件/附件”打分排序（后缀、附件/下载字样、同域加分，导航/页脚降权），正文先做主体区域提取（`main`/`article`/`#content` 等）再截断，另附 `headings` 与 `stats`（原始链接数、正文总长度）。观察结果新增 `stats`，便于判断剪枝力度。
- **等待策略**：不再使用 `networkidle`（长连接页面会白等到超时，实测比冷启动还慢），改为等到正文出现即返回。
- **提示词**：观察结果改用紧凑 JSON 序列化，并对总长度设置上限。
- **检索词数量**：新增 `AgentConfig.max_search_queries`（默认 3），限制每次运行加载的搜索结果页数量。
- **节点耗时记录**：`graph.py` 用 `_timed()` 包装全部节点，`trace[*].elapsed_ms` 记录每步耗时，`final.timings` 与 `final.total_elapsed_ms` 做汇总，便于直接定位瓶颈（例如《电梯用钢丝绳》一次运行 30.6s 中，`download` 18.0s、`choose_download` 7.3s、`search` 3.7s）。

### 5. 下载按钮走 `window.open` 弹窗，导致真正的附件被漏掉

`openstd.samr.gov.cn` 的“下载标准 / 在线预览”都是：

```js
function showGb(gbCode, type){
    var url = "/bzgk/std/showGb?type="+type+"&hcno="+gbCode;
    window.open(url);
}
```

原来的 `click_download` 只用 `page.expect_download()` 监听当前页面，并靠“当前页 URL 是否变化”判断是否发生导航，因此弹窗里触发的下载完全捕获不到，只会报“点击下载按钮后没有产生下载或文件导航”。结果是退化成 `save_page_pdf`，拿到 2 页的元数据页导出，而真正的标准正文（43 页、1.8 MB）被丢掉。

现在 `click_download` 在 **context 级别**收集下载事件，因此同时覆盖“当前页直接下载”“弹窗内触发下载”“点击后页面导航到文件 URL”三种情况；如果按钮弹出了新窗口但没有触发下载（例如在线阅读器），则记录新地址交给状态图重新观察，而不是直接判定失败。

> 实现注记：事件处理器必须是普通 Python 函数，不能直接传 `list.append` 这类 builtin 方法。Playwright 的同步封装会对处理器对象执行 `setattr(handler, "_pw_impl_instance_", wrapper)`，builtin 方法没有 `__dict__`，会抛 `AttributeError: 'builtin_function_or_method' object has no attribute '_pw_impl_instance_'`。

### 6. 只拿到网页导出时不再冒充成功

`save_page_pdf` / `click_print` 得到的是网页快照而非原始附件，但此前仍返回 `success`，并且还会被重命名成“目标文件名_标准编号.pdf”，看起来像官方原件。现在：

- 这两种动作的结果状态为 `page_export_only`，与 `success` 区分开；
- 不按目标文件名重命名，保留 `page_export.pdf` / `printed_page.pdf`；
- `verification.warnings` 中注明“保存的是网页导出的 PDF，不是原始附件”；
- 规划器提示词中明确：只要存在可行的下载控件或附件链接，就优先选择它们而不是 `save_page_pdf`。

### 7. 其他

- `download_direct` / `inspect_embedded` 直接复用浏览器上下文的会话发起请求，不必先打开页面再取文件；
- `follow_attachment_page` 指向 HTML 附件页时改为“进入并重新观察”，而不是把 HTML 当文件存盘；
- 搜索引擎与页面浏览器共用同一个 Playwright 实例（`runtime.py` 引用计数）：Playwright 同步 API 会在当前线程驱动 asyncio 事件循环，同线程启动第二个实例会抛 `using Playwright Sync API inside the asyncio loop`。

### 8. 生命周期把关前移，废止页面不再浪费一次大模型调用

节点顺序由

```text
observe → choose_download → check_lifecycle → download
```

调整为

```text
observe → check_lifecycle → choose_download → download
```

`check_lifecycle` 只依赖页面文本、耗时 0 毫秒且不消耗 token，把它放在花钱的决策之前，遇到判定为 `withdrawn` / `ambiguous` 的页面可以直接跳 `report`，省下一次完整的大模型调用（实测约 7.5 秒、约 1.8k token）。现行性判定与“选哪个下载动作”互不依赖，因此调换不影响决策质量。

### 9. token 用量可观测

`LLMDownloadPlanner` 改用 `with_structured_output(DownloadPlan, include_raw=True)`，从原始响应里取回 token 用量：

- `trace[*].details.usage`：每次决策的 `input_tokens` / `output_tokens` / `total_tokens`；
- `final.usage_total`：整条流程的合计。

同时 `summarize_html()` 的 `stats` 新增 `html_chars`，记录解析前的原始 HTML 体积，便于直接看到“HTML → 提示词”的压缩比。以《电梯用钢丝绳》为例：原始 HTML 22,045 字符 → 发给大模型约 2,600 字符（约 12%），单次决策输入 1,531 token。

> 需要说明：**HTML 从不进入提示词**。`observe` 阶段用 BeautifulSoup 在本地解析 HTML，剔除 script/style/nav/header/footer，只提取正文主体与结构化链接列表，再序列化为紧凑 JSON 交给模型。

### 10. 无扩展名附件的类型识别

部分政府站点的附件 URL 不带扩展名（住建部 `art_17339_761192.html` 页面里的附件就是如此）。这类文件落盘后没有后缀，会连带出三个问题：

- `mimetypes` 推断不出类型，`mime_type` 为空；
- `verify_file()` 用 `suffix == ".pdf"` 判断是否解析，于是跳过整个 PDF 分支——不解析页数、不提取标准编号、不做标题匹配，**却因为“size > 0 且无警告”返回 `ok=True`**；
- 重命名用源文件的 `suffix` 拼接，产出 `工程结构通用规范` 这种没有扩展名的文件，双击打不开。

现在 `verify_file()` 在扩展名缺失或类型未知时**按文件头嗅探**：

| 文件头 | 判定 |
| --- | --- |
| `%PDF-` | `application/pdf` → `.pdf` |
| `PK` + 压缩包内包含 `word/` / `xl/` / `ppt/` / `OFD.xml` | docx / xlsx / pptx / ofd |
| `PK` 开头的其他压缩包 | `application/zip` → `.zip` |
| OLE2 复合文档文件头 | `application/x-ole-storage`（doc/xls/ppt 共用此文件头，不猜扩展名）|

嗅探结果写入 `verification.metadata.detected_extension`，重命名时用它补扩展名，PDF 解析分支也按嗅探结果进入。若文件名无扩展名且文件头也无法识别，则记入 `warnings`，`ok` 变为 False——不再把无法识别的文件当成成功。

顺带把 `sha256` 改为分块读取：修复前 `read_bytes()` 会把整个文件读进内存，而批量测试中已出现过 65 MB 的规范 PDF。

实测（《工程结构通用规范》，住建部）：修复前产出无扩展名文件、`pages=None`；修复后产出 `工程结构通用规范.pdf`、`mime=application/pdf`、30 页。

## 批量并行运行

多个文件可以并行处理，每个任务一个独立进程：

```powershell
cd <本仓库>
conda activate <本仓库>\.conda-env
python -m standards_crawler_agent.batch "电梯用钢丝绳" "建筑防火通用规范" "工程结构通用规范" --jobs 3
```

- **为什么用进程而不是线程**：Playwright 同步 API 把 asyncio 事件循环与 greenlet 调度器绑在创建它的线程上——同一线程不能有两个实例（会报 `using Playwright Sync API inside the asyncio loop`），实例也不能跨线程使用。`runtime.py` 是进程级单例，因此独立进程是最干净的做法。
- **为什么可以共用一个 `downloads/`**：最终文件名由请求名生成（`{请求名}_{标准编号}.pdf`），不同任务的目标文件不同，产物名天然不同。唯一会撞的是 `save_page_pdf` / `click_print` 的两个常量文件名，现已加上进程号后缀（`page_export_<pid>.pdf`、`printed_page_<pid>.pdf`），并发进程不会互相覆盖。
- 批量驱动会自动**跳过重复的请求名**（指向同一目标的条目会写出同一个最终文件）。
- `--jobs` 并行度（默认 3）、`--stagger` 启动错峰秒数（默认 2，避免同时打搜索引擎触发风控）、`--timeout` 单任务超时（默认 120 秒；配合 `--retries 1`，单任务最坏耗时约 240 秒）、`--output-root` 产物根目录。
- 产物结构：`results/batch_<时间戳>/<序号_文件名>/{result.json, run.log}`，以及汇总文件 `batch_summary.json`（含每个任务的状态、耗时、token、失败原因）；下载文件统一落在 `downloads/`。
- 资源约束：内存约为 `jobs × 150~300 MB`（每个 headless Chromium 一个进程）；大模型调用次数随任务数线性增长，是并行后最可能先撞到的限制。

### 11. 名称笔误的纠错检索

编制依据表里的名称常有笔误。实测把《高层民用建筑钢结构技术**规程**》（JGJ 99-2015）写成“技术**规范**”后，按原名做精确短语检索**完全找不到官网**——搜索引擎返回的是“高层建筑有多少层”这类科普内容，候选里根本没有标准委页面。

`build_queries()` 因此增加一条**去文种词的核心名称检索**：

```text
"高层民用建筑钢结构技术规范"      ← 原名，精确短语
"高层民用建筑钢结构"              ← 核心名称，去掉“技术规范”
"高层民用建筑钢结构技术规范" 最新 现行
```

去掉“规范”之后，“规程 / 规范 / 标准”都能匹配上同一份文件。文种词表见 `DOC_TYPE_SUFFIXES`（技术要求/技术条件/技术规程/技术规范/技术标准/规范/规程/标准/规定/办法/通知/细则/导则/指南/规则），且只有核心名称长度 ≥ 6 时才生成，避免对“中华人民共和国突发事件应对法”这类名称产生无意义查询。

规划器提示词同步放宽：页面标题与请求名称**只有文种词差异**时视为同一份文件，并要求在 `reason` 里写出实际匹配到的正式名称。

实测：`关于印发《山东省房屋建筑和市政基础设施工程危险性较大分部分项工程安全管理实施细则》的通知` 由 `not_downloadable` 变为成功命中山东省政府官网。

### 12. 直链下载改用浏览器会话、selector 容错

**① `download_direct` 之前绕开了浏览器会话。** `graph.download` 直接调用 httpx 版 `download_direct()`，而 `PlaywrightBrowser.execute()` 里那条用 `context.request`（带 Cookie / UA / Referer）的分支从未被调用——是死代码。实测上海住建委的 PDF 对裸 HTTP 客户端返回 `403 Forbidden`，导致“已经找到完全正确的文件却下不来”。

现在优先走浏览器上下文，失败再退回 httpx 流式下载。实测《混凝土结构施工质量验收规范》从 `not_downloadable` 变为成功下载 **140 页、4.65 MB** 的 `混凝土结构施工质量验收规范_GB 50204—2015.pdf`。

> 启用这条死代码后立刻暴露：Playwright 的 `APIResponse` 只有 `ok` / `status` / `status_text`，**没有 httpx 的 `raise_for_status()`**。已改为 `_ensure_ok(response)`。

**② 模型给出的 selector 可能是纯文本。** 实测模型返回过 `2.《混凝土结构工程施工质量验收规范》（GB 50204-2015）.pdf`，直接交给 `page.locator()` 会被当成 CSS 解析并报 `Unexpected token "."`。新增 `_locator()`：带引擎前缀（`text=`/`css=`/`xpath=`）或形似 CSS 的原样透传，否则改用 `text=` 引擎。

### 13. 生命周期判定重构与两项保护

**判定依据改为三层**（`detect_lifecycle_status(page_text, subject=..., snippet=...)`）：

1. **页面正文里目标名称附近**（±120 字符）的文本；
2. **搜索结果摘要里“名称 + 存废词”紧邻**（±60 字符）——列表页的摘要本身带状态标记；
3. **正文里压根没出现目标名称时不做废止判定**。

第 3 条是实测踩出来的：落到政府门户首页时，首页上**别的文件**的“废止”会把目标名称误判成废止（该任务因此从 `not_downloadable` 变成 `skipped_withdrawn`，0 token 直接收工，完全错误）。

第 1 条则来自另一个实测：应急管理部页面上《生产安全事故应急条例》被判“停止执行”，原因是**该条例第二十五条正文里**写着“……应当决定停止执行依照本条例和有关法律、法规采取的全部或者部分应急救援措施”。整页关键词共现把法规正文当成了存废标记。

**新增两项保护：**

- **空白页保护**：观察结果正文 < 50 字符且无任何链接时视为观察失败，自动换下一个候选。实测国家法律法规数据库的跳转链接返回 39 字符空壳页，此前会让模型对着空页面说 `no_download` 然后收工。
- **候选可信度门槛**：`AgentConfig.min_candidate_score`（默认 0.35，按 `0.5×官方分 + 0.5×页面分`）。搜索引擎无命中时会解析出无关链接（实测出现过百度首页、剑桥词典、查字典），门槛让这些候选直接出局，**不白烧一次大模型调用**（0 token 收工）。

### 14. 下载文件的命名

命名规则是 `名称_编号.扩展名`（没有编号时就是 `名称.扩展名`）。修复前实测出四个问题：

| 问题 | 实测表现 |
| --- | --- |
| 网页导出没有名字 | `page_export_14224.pdf`、`page_export_3360.pdf`…… 进程号后缀本来只是跑批时防冲突的临时名，却直接成了交付物 |
| 名称继承输入里的笔误 | 落盘 `混凝土结构施工质量验收规范_GB 50204—2015.pdf`，而正式名称是《混凝土结构**工程**施工质量验收规范》 |
| 编号经常提取不到 | 只有 PDF 正文能被解析出编号，网页导出与 docx 附件一律没有编号 |
| 编号写法不统一 | 落盘用全角破折号 `GB 50204—2015`，与编制依据表里的 `GB50204-2015` 对不上 |

**数据来源的改动：**

- `DownloadPlan` 增加 `matched_title` 与 `standard_number` 两个字段，由模型在观察页面时回填：正式文件名称、页面上明确写出的标准号/文号。提示词明确要求“名称有笔误时填页面上的正式名称”“页面上没有编号就留空，不要自行推断”。
- `build_canonical_filename()` 优先使用 `matched_title`，并对它做体检（`acceptable_title()`）：长度 4~80、不含“首页/登录/网站/平台/门户/百科/导航”这类字样、与请求名的字符重合度不低于 50%。体检不通过就回退到请求名，避免把手误的站点名当文件名。
- `normalize_standard_number()` 统一编号写法：`—`/`–`/`－`/`−` 等破折号统一成半角 `-`，全角 `／` 统一成 `/`，去掉连字符两侧空格。元数据里存半角形式，落盘时由 `safe_filename_part()` 转成全角以符合 Windows 文件名限制。
- 标准号优先级：模型在页面上识别到的 → PDF 正文提取的。正文提取对扫描件、字体编码异常的 PDF 常常失败，模型这一路补上了缺口。
- **网页导出也按规范名落盘**，不再泄漏 `page_export_<pid>.pdf`；性质靠 `status = page_export_only` 与 `verification.warnings` 区分。

**顺带修掉的一个 bug：** 网页 PDF 导出会被截断。实测同一个 gov.cn 页面，作为首个动作立刻导出只有 **1 页**（75 KB），而点过一轮下载失败、页面开了十几秒后再导出是 **18 页**（375 KB）。原因是内容尚未渲染完就调用了 `page.pdf()`。现在统一走 `_export_pdf()`：先等 `load` 状态（最多 5 秒），再静置 800 ms 才导出。

**实测效果：**

| 请求名 | 落盘名 |
| --- | --- |
| 混凝土结构施工质量验收规范（少一个“工程”）| `混凝土结构工程施工质量验收规范_GB 50204-2015.pdf`（140 页）|
| 房屋市政工程生产安全重大事故隐患判定标准（2024版）| `房屋市政工程生产安全重大事故隐患判定标准（2024版）_建质规〔2024〕5号.docx` |
| 中华人民共和国突发事件应对法 | `中华人民共和国突发事件应对法.pdf`（18 页，网页导出）|

#### 命名策略（已确认）

文件名中的**名称优先使用模型在页面上识别到的正式名称**，而不是用户请求的名称。这样编制依据表里的笔误会被自动纠正——实测把《混凝土结构工程**施工**质量验收规范》写成《混凝土结构施工质量验收规范》时，落盘仍是正式名称。

代价是：当页面主体文件与请求名指向不同文书时，文件名会采用页面正文的正式名称。实测请求“关于印发《山东省房屋建筑和市政基础设施工程危险性较大分部分项工程安全管理实施细则》的通知”，而该页正文主体是《…实施细则》本身，最终落盘为：

```text
山东省房屋建筑和市政基础设施工程危险性较大分部分项工程安全管理实施细则_鲁建质安字〔2024〕6号.pdf
```

而不是表格里的“关于印发《…》的通知_鲁建质安字〔2024〕6号.pdf”。**这是有意选择的结果**：优先保证“文件与官方正式名称对得上”，而不是“与请求字面一致”。若日后更希望与表格字面一致，把 `build_canonical_filename()` 里 `matched_title` 的优先级去掉即可（保留编号来源与归一化逻辑）。

### 15. 观察结果只保留真实可见的控件

实测 std.samr.gov.cn 的地方标准详情页：「查看全文」按钮在 DOM 里存在，但**是隐藏的**。

```text
<button class="catalog-btn btn btn-primary openhdbpdf">查看全文</button>
  visible=False   box=None
普通点击        → 超时
滚动到元素      → 也超时
强制点击(force) → Element is not visible
```

`summarize_html()` 用 BeautifulSoup 解析 HTML，**看不出元素的可见性**，于是把这个点不动的按钮列成了可用控件。模型据此连续两轮选择点击它（每轮 8 秒超时），失败后只能退化成导出页面——而该页面是**注册墙**（推荐性地方标准在此平台不公开全文）。

现在 `PlaywrightBrowser.observe()` 会先用一段 JS 取回每个控件的真实可见性，再由 `drop_hidden_controls()` 处理：

- **隐藏的按钮**：剔除（点不动，留着只会让模型反复尝试）；
- **隐藏的链接**：保留——它们往往仍是可直链下载的 URL，不少站点把下载入口放在 `display:none` 的 `<a>` 里靠 JS 触发；
- 同名控件中只要有一个可见，就不判定为隐藏；
- 剔除数量记入 `stats.buttons_hidden_filtered`，隐藏链接数量记入 `stats.links_hidden`。

**实测效果**（《建筑与市政基坑工程监测技术标准》，DB37/T 5313-2025）：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 首个动作 | `click_view_original`，selector=`button:text-is('查看全文')`（隐藏按钮）| `click_view_original`，selector=`text=查看文本`（可见元素）|
| 过程 | 两次点击超时后放弃 | 跳转到地方标准门户 → `click_download` |
| 结果 | 导出 3 页注册墙页面 | **下载到 144 页正式标准**（697,274 字节）|

### 17. 搜索结果相关性闸门

批量连续检索时，搜索引擎（当前用 Bing 页面解析）**会返回与查询完全无关的结果**。实测一次批量运行中，查询「济南市住房和城乡建设局关于进一步加强全市房屋建筑和燃气供热工程危险性较大分部分项工程管理的通知」，30 条结果全部是：

```text
[www.landrover.com.cn]  路虎 | 了解豪华SUV和4x4车型
[jxc.landrover.com.cn]  嘉兴伟杰智选汽车销售服务有限公司
[www.zhihu.com]         怎样高效丰富bilibili弹幕/用户屏蔽列表？
[www.52pojie.cn]        B站视频下载器 Bili23-Downloader
```

这类结果有两个后果：被 `min_candidate_score` 门槛全部筛掉时任务以「未发现候选页面」收工（0 token）；若没有门槛，状态图会去观察路虎官网这类页面。

现在 `search` 节点对每个查询的结果做一次粗判（`looks_relevant()`：查询字符集在标题+摘要中的覆盖率是否达到 30%）：

- 判为无关 → 等 2 秒重试一次；
- 重试仍无关 → **丢弃该查询的结果**并记入 `errors`，不让垃圾进入候选池。

对照实验说明这**不是并发导致**的：3 个并发查询与串行执行的结果完全一致（同样的 12 条官网域名、同样的 30 条结果、连垃圾项都相同）。更可能是短时间内累计检索次数触发了限流。这对批量运行很重要——424 条任务会产生上千次检索。

### 18. 关于「先找发布单位，再回官网检索」这条思路的调查

实测结论（同一台机器、同一网络、真实 Bing）：

| 做法 | 结果 |
| --- | --- |
| 完整文件名检索 | ✅ **稳定命中目标文件**，域名包含 `jncc.jinan.gov.cn`、`jnggzy.jinan.gov.cn`、`www.jinan.gov.cn` 等官网，以及转载该文件的第三方站 |

| `site:jinan.gov.cn 危险性较大分部分项工程 通知` | ❌ 返回 Poki、Playhop 等**在线小游戏**站 |

### 19. 站内检索兜底（site_search）

**触发原则：现有方案优先，走不通时才启用。** 状态图先照常尝试候选页上的直链、下载控件、页面导出；只有以下情况才走站内检索：

- 候选**全部低于可信度门槛**，但搜索结果里有官方网站 → 把官网入口页作为唯一候选，并在观察结果中附加 `official_site_entry` 提示；
- 模型在官网首页/栏目页上找不到目标文件时，选择新增的 `site_search` 动作。

**执行方式**（`browser.py`）：在当前页面按一组常见形态定位可见搜索框（`input[type=search]`、`input[name=q]`、`input[class*=search]`、`input[placeholder*=搜索/关键字/检索]` 等），填入 `search_query` 并提交；结果页若以新窗口打开（`target=_blank`）则跟随弹窗，否则看当前页是否跳转；随后状态图重新观察该结果页。`after_download` 已把 `site_search` 与 `click_view_original` 同等对待。

`search_query` 由模型填写，优先文号/标准号，其次文件名关键部分。

#### 实测：为什么必须限定"只在官网"以及提示词要写重

同一台机器、同一网络，对 `jncc.jinan.gov.cn`（济南市住建局官网）实测：

| 做法 | 结果 |
| --- | --- |
| `site:jncc.jinan.gov.cn 危险性较大分部分项工程` | ❌ 返回知乎的**电车续航**讨论——`site:` 被引擎忽略 |
| `site:jinan.gov.cn 危险性较大分部分项工程 通知` | ❌ 返回 Poki、Playhop 等**在线小游戏**站 |
| 只用文号 `"济建质安字〔2025〕1号"` 做全网检索 | ❌ 返回汉典、新华字典的「济」字释义 |
| **官网站内检索**文号 `济建质安字〔2025〕1号` | ✅ 结果第 1 条即目标文件页面 |
| **官网站内检索** `危险性较大分部分项工程` | ✅ 第 8 条即目标文件页面 |

因此 `site_search` **只对官方网站使用**，提示词里明确写了"非官方网站不要使用此动作"，并要求：页面上只有栏目导航（通知公告/下载中心/政策法规）时，**不要逐个点栏目翻页，先用站内检索**——实测模型最初正是选择了逐个点栏目，烧掉 5 轮 22k token 且点错文件。

### 20. 异步渲染页面的等待修复

站内检索的结果页是**异步渲染**的：静态外壳（导航 + "抱歉，在当前分类下均未找到" 占位 + 热门搜索）很快超过 `innerText > 200` 的阈值，真正的结果稍后才注入。原来的等待策略在阈值满足后只多等 200ms，于是抓到空壳页面 —— 模型读到"未找到相关信息"，判定检索失败，**连续重新检索了 5 次**。

现在 `_open()` 在阈值满足后再观察**链接数量是否还在增长**：还在增长就继续等（每次 500ms，最多 6 次），稳定后立即返回。修复后同一结果页的观察结果：

```text
危险性较大分部分项工程管理 的最新相关信息
  济南市住房和城乡建设局关于进一步加强全市房屋建筑和燃气供热工程危险性较大分部分项工程管理的通知
  2025-01-02  通知公告
  文件编号:济建质安字[2025]1号  发布机构:市住建局  来源:济南市住房和城乡建设局
```

代价是每个静态页面多约 1 秒（需要两次采样确认稳定），换来异步页面不再抓空。

`site_search` 只在济南市住建局官网验证过，因此拿 7 个不同类型的政府官网做了通用性测试（走的就是 `browser.execute` 里的通用逻辑，没有任何站点特判）：

| 站点 | 补强前 | 补强后 | 说明 |
| --- | --- | --- | --- |
| 中国政府网（国家级门户）| ✅ | ✅ | 跳转 `sousuo.www.gov.cn/sousuo/search.shtml`，结果直接可读 |
| 住建部（部委）| ✅ | ✅ | 跳转 `…/api-gateway/jpaas-jsearch-web-server/search`，60 条链接 |
| 应急管理部（部委）| 跳转成功、结果页空白 | ✅ 跳转成功 | 结果页是 TRS 框架（正文仅 9 字符 `TRSWAS5.1`），需 iframe 处理 |
| 国家标准委（行业平台）| ❌ 找不到搜索框 | ✅ | 跳转 `/search/std?q=…`；结果仍需更长等待或异步处理 |
| 山东省住建厅（省级）| ✅ | ✅ | 跳转 `jsearchfront/search.do`，31 条链接 |
| 上海市住建委（市级）| ❌ 提交无效 | ✅ | 跳转 `/websearch/#search/query=…`，33 条链接 |
| 济南市政府门户（市级）| ✅ | ✅ | 同 JPAAS 平台，60 条链接 |

**结论：提交并跳转到结果页 7/7 可用；其中 5 个结果页可直接观察到有效内容，2 个（应急管理部、国家标准委）跳转成功但结果页需要额外处理。**

两个原失败案例的成因都是"形态差异"，不是逻辑不通：

- **国家标准委**：输入框的 `placeholder` 是「请输入**关键**词」，而选择器原本只写了「关键**字**」；
- **上海市住建委**：搜索框没有 `<form>`，`target="_blank"` 挂在 `<div>` 上，提交靠 JS 绑定，因此回车与常见按钮选择器都无效。

**补强（三道通用兜底）：**

1. 选择器补充 `input[placeholder*=关键词]`；
2. 定位不到时用 JS 找出页面里**唯一**的（或位于 class/id 含 `search` 容器内的）可见文本框，打上 `data-dsh-search` 标记后再用 Playwright 定位；
3. 提交后地址没变化时，在输入框父级容器（最多向上 3 层）内寻找可见的提交控件——先找文字含「搜索/检索/查询」的，再退而找 class 含 `btn/icon/submit/search` 的**纯图标按钮**；仍无效则尝试 `form.submit()`。

`site_search` 仍然只在官方网站上使用（提示词约束"非官方网站不要使用此动作"）。

### 23. 状态语义：网页导出算成功

`page_export_only` 改名为 **`success_page_export`**。理由：法律、行政法规、地方规章在很多官网上**就是以 HTML 正文形态发布的**，页面导出即其官方发布形态，内容正确就不该算失败；但仍与"下载到官方原件"（`success`）区分开。批量汇总相应改为按 `success` 前缀统计，并给出明细：

```text
成功 N/9（官方原件 X，网页导出 Y，扫描件 Z）
```

> 后续补充：第 34 节给"网页导出算成功"补上了**前置条件——产物里必须真有文件正文**。原来只要页面标题能对上就算成功，导致 30 个标准著录页/文库付费外壳被判成功；同时新增 `success_scanned`（扫描件单列）。

### 24. 撤回一次把假成功引进来的"优化"

**背景**：候选本身是文件直链时（例如 `www.jinan.gov.cn/attach/0/….pdf`），`page.goto` 会抛 `Page.goto: Download is starting`。原行为是把它记为"观察失败"→ 状态图自动切下一个候选。

**当时的改动**：把这种情况伪造成"这是文件直链，请用 download_direct 下载它"的观察结果交给模型，理由是"少浪费一轮"。结果实测《济南市…危大工程管理的通知》**下到了该局 2020 年的另一份文件**（济建建管字〔2020〕48号，关于项目交易文件在线监督管理），而且报 `success`——`verify_file` 算出的 `title_matches` 为空，但状态图从未使用该字段。

**现已撤回**，恢复"观察失败 → 自动换候选"。同一个任务在撤回后重新走通：直链候选被跳过 → 进入 jncc 官网 → 站内检索 → 官方详情页 → 导出正确文件。

> 教训：把"失败信号"改造成"看起来成功的信号"要非常谨慎——它绕过了候选切换这条安全网。

### 25. 下载内容相关性校验

即使不走上述路径，任何候选都可能下到"有效但不对"的文件。现在 `verify_file()` 会校验下载内容是否确实是目标文件：

- `looks_readable_text()`：判断 PDF 文本层是否可读（扫描件、字体编码异常的文本层会抽出乱码，实测《工程结构通用规范》首页抽出 `OOb?W蜰a^鷭緪鐿醏oQl_`）。判据是高频汉字占比 ≥ 1% 且长度 ≥ 120 字符。**文本层不可读则跳过校验**，避免误伤正确文件。
- `name_segments()`：把请求名称切成有辨识度的片段。按片段而不是按单字覆盖率校验很重要——实测那份下错的文件与目标文件同属济南市住建局、都涉及房屋建筑和燃气供热工程，单字覆盖率并不低，但缺少"危险性较大分部分项工程"这类片段。
- `check_name_match()`：片段命中率低于 60% 即判为不匹配，写入 `verification.warnings`，`ok` 变为 False，状态图据此切换候选。命中情况记入 `metadata.name_match`（如 `名称片段命中 1/2`）。

**实测**：磁盘上那份下错的文件现在会被判为失败：

```text
济南市…通知.pdf   ok=False   warnings=['下载内容与目标名称不匹配（名称片段命中 1/2）']
电梯用钢丝绳_GB 8903-2024.pdf   ok=True   name_match=名称片段命中 1/1
```

### 26. 选择器命中多个元素时挑第一个可见的

搜索/列表页里同一个 URL 常常出现多次（实测济南那条的结果页里目标链接有 3 个 `<a>`，前两个在隐藏的"全部"折叠区里）。`_locator()` 原来返回 `.first`，于是**永远点到不可见的那个**，连点 4 次、每次 8 秒超时。

现在 `_locator()` 会遍历最多 10 个匹配，返回**第一个可见的**；全部不可见时回退到 `.first`。与搜索框定位（`_first_visible`）保持同一策略。

### 28. 内容校验的误杀与修正

第 25 节的内容校验上线后立刻误杀了一次正确文件：

```text
observe  zjw.sh.gov.cn（上海住建委）
  → download_direct  → 4,653,870 字节 / 140 页的《混凝土结构工程施工质量验收规范》
verify: ok=False  name_match=名称片段命中 0/1        ← 误杀
retry_candidate
observe  mohurd.gov.cn
  → download_direct  → 75 页扫描件（文本层乱码）
verify: ok=True   name_match=文本层不可读，跳过校验   ← 放过更差的文件
```

根因是**把请求名当成了标准答案**：请求名是“混凝土结构施工质量验收规范”（漏了“工程”），而官方正式名是“混凝土结构**工程**施工质量验收规范”，按整段匹配必然 0 命中。

修正为**两条判据满足其一即通过**：

- 名称片段命中率 ≥ 60%（名称准确时最可靠）；
- **名称字符覆盖率 ≥ 90%**（名称有笔误、漏字时兜底）。

实测三个样本：

| 样本 | 结果 |
| --- | --- |
| 漏“工程”的请求名 + 正确标准文本 | 通过（片段 0/1，**字符覆盖 100%**）|
| 济南请求名 + 该局 2020 年的另一份文件 | 拒绝（片段 1/2，字符覆盖 85%）|
| 济南请求名 + 正确文件 | 通过（片段 2/2，字符覆盖 100%）|

阈值取 90%：漏字样本是 100%，下错样本是 85%，余量足够。乱码文本层仍然跳过校验，不误伤。

> 教训：任何"拒绝"型校验都要考虑**误杀后换候选会不会更差**。这次误杀把一个正确文件换成了更差的扫描件。

### 29. 页面稳定性等待改为有超时的实现

第 20 节那轮批量里，济南任务 **600 秒超时、token 为 0**——说明在调用大模型之前就卡住了，而且是死等（`--timeout` 是外层兜底）。原实现用 `page.evaluate()` 采样链接数：

```python
count = page.evaluate("document.querySelectorAll('a[href]').length")
```

`page.evaluate` **没有超时参数**，页面处于导航或忙碌状态时可能一直阻塞。现改为一次有界的 `wait_for_function`（`polling=200, timeout=3000`），条件本身即"连续两次采样链接数一致"：

```python
page.wait_for_function(
    """() => {
         const count = document.querySelectorAll('a[href]').length;
         if (window.__dshLastLinkCount === count) return true;
         window.__dshLastLinkCount = count;
         return false;
       }""",
    polling=200,
    timeout=3_000,
)
```

效果：稳定性等待仍是自适应的，但最坏 3 秒返回，不会无限阻塞。改造后同一批 9 个任务的墙钟从 **636 秒降到 173.5 秒**，济南任务本身由 600 秒超时变为 **52.9 秒成功**。

### 30. 只采集 `<button>` 标签会漏掉可见的入口

《建筑与市政基坑工程监测技术标准》这条任务在批量里稳定失败：模型在 std.samr.gov.cn 的地方标准详情页上**连点 5 次隐藏的"查看全文"按钮**，每次 8 秒超时，共烧掉 40 秒与 5 次大模型调用。

排查后发现页面上有**两个 class 相同、触发同一个 JS 处理函数**的入口：

```html
<!-- 手机端专用：Bootstrap 的 visible-xs -->
<button class="catalog-btn btn btn-primary openhdbpdf">查看全文</button>   ← 隐藏
<!-- 左侧边栏，桌面端可见 -->
<div class="sidebar-btn openhdbpdf"><span>查看文本</span></div>            ← 可见
```

两者的处理函数都是：

```javascript
$(".openhdbpdf").click(function(){
    if(isAppPlus){ ... }
    else { window.open('https://dbba.sacinfo.org.cn/portal/online/…', '_blank'); }   // 开新窗口
})
```

**点击超时与"开新窗口"无关**——`click_view_original` 本来就有弹窗处理（`expect_popup` 失败则看当前页地址变化）。真正的原因是：

- 隐藏的那个 `<button>` 被可见性过滤正确剔除；
- 可见的那个是 `<div class="sidebar-btn">`，**不是 `<button>` 标签**，而 `_collect_buttons()` 只采集
  `button / input[type=button] / input[type=submit] / [role=button]` → **完全没采集到**；
- 于是观察结果的 `buttons` 里只剩一个"登录"，模型只能从**正文文本**里读到"查看全文"字样，就去点那个隐藏元素。

**修正**：可见性探测的 JS 把 `[class*=btn]`、`[onclick]` 也纳入，并将其中**可见、且观察结果里还没有**的条目补进 `buttons`。补入条件收紧为"像按钮"——标签是 `button`/`input`、或 class 含 `btn`/`button`、或带 `onclick`；纯 `<a>` 导航链接不补（它们本来就在 `links` 里）。

修正后同一页面的观察结果：

```text
=== 观察结果里的按钮 ===
  <button> '登录'
  <a>      '注册'
  <div>    '查看文本'      ← 可见入口，此前完全没被采集
  （共 3 个，过滤掉隐藏的 2 个）
```

**效果**：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 动作路径 | 连点隐藏的"查看全文"5 次，每次 8 秒超时 | 点可见的"查看文本" → `window.open` → dbba 门户 → "下载标准" |
| 耗时 | 125.6 秒 | **27.0 秒** |
| token | 22,844 | **5,922** |
| 结果 | `not_downloadable` | **144 页正式标准**（`success`）|

> 教训：观察结果的 `buttons` 是模型唯一的"可点选项"来源。凡是**可点但不是 `<button>` 标签**的元素（`div.btn`、`span[onclick]`、`a.btn` 等），漏采就会让模型退而求其次，去正文里找一个点不动的隐藏控件。

### 31. 假成功的四道防线（扩展名 / 校验不得跳过 / 模型声称的名称 / 打印片段）

**背景**：r7、r10、r12、r13、r15、r16 六轮批量里，同一条任务都拿到同一件"假成功"产物：

```text
downloads\关于印发《山东省…》的通知.jsp    612,407 字节 / 4 页
  verify: ok=True   title_matches=[]   warnings=[]
  实况: 页脚反复出现 14/17、15/17、16/17；正文只有附件条目（第一章…第七章全缺）
        模型自己填的 matched_title 是"专项施工方案论证结论为“不通过”的情形"
        —— 那是公报刊表页上另一份公文的附件
```

三处漏洞叠在一起才让它过关：扩展名是下载端点名 `.jsp`（不是已知文档扩展名），旧逻辑只按扩展名判断类型，于是**压根没进 PDF 内容校验分支**；内容校验的判据只有名称匹配，而它的页眉恰好带着完整标题（`名称片段命中 1/1，字符覆盖 100%`）；模型认错目标的信号（`matched_title`）只被用在**命名**上，从不参与**校验**。

**修复（`download.py` + `graph.py`）**

1. **类型以文件头为准**（`resolve_file_type`）：扩展名缺失、不在已知文档扩展名集合里、或与文件头冲突时，一律按文件头纠正，并把应采用的扩展名通过 `metadata.canonical_extension` 交给重命名——端点名 `downfile.jsp` 不再可能留在产物名里。
2. **内容校验不得静默跳过**：文件头判定为 PDF 就必须走内容校验，没跑成（解析不出文本层）直接记 warning 判失败，不允许"没校验=通过"。
   > 附带更正：原先设想"`title_matches` 为空即判失败"，实测会**误杀**《混凝土结构工程施工质量验收规范》那类正确文件（`title_matches` 是按空格切词的产物，中文名整段无空格时天然为空；真正的判据是 `metadata.name_match`），因此改为"不允许跳过"而不是"为空即失败"。
3. **模型声称的名称参与校验**（`check_claimed_title`）：`matched_title` 与请求名字符重合度 < 50% 时判为下错文件。这一条有实测依据——**79 次填了 `matched_title` 的决策里只有 6 次重合度不达标，而这 6 次全是同一件下错的文件**；与站点名/栏目标题这类常见噪声分开，避免误杀。
4. **打印片段检测**（`detect_print_fragment`）：同一个页码分母重复出现（打印稿每页都有页脚）且大于文件实际页数 → 判为片段。上例中 `14/17`、`15/17`、`16/17` 出现 3 次而文件只有 4 页；日期（`2025/1/15`）与孤立比例（`3/8`）都不误判。
5. 顺带补一道兜底：`verify_file` 里 `text/html` 一律判失败——直链守卫只管住了下载那一刻，早期版本曾把通知页存成 `.html` 并报 success。

**效果（r17 实测，`downloads/` 清空后重跑）**

```text
choose_download  download_direct → downfile.jsp
verify           ok=False  warnings=[
                   '文件扩展名 .jsp 与实际类型不符（实际为 .pdf），已按实际类型校验与命名',
                   '模型声称的目标文件名称与请求名称无关（“专项施工方案…”，重合度 13%），判定为下错文件',
                   '疑似网页打印片段：文中页码标记显示共 17 页（如 14/17），但文件只有 4 页，正文可能不完整']
retry_candidate  → zjt.shandong.gov.cn（第 2 候选）
verify           ok=True   8 页，含第一章/第一条/第七章 + 鲁建质安字〔2024〕6号，状态 success_page_export
```

那件假成功变成了**完整正确的结果**，状态也诚实地标成网页导出（不再计入"官方原件"）。同一批：**8/9 成功（官方原件 3 + 网页导出 5）、墙钟 85.5 秒、73.2k token**，唯一失败仍是《高层民用建筑钢结构技术规范》（搜索引擎层面）。代价是 #5 多做一轮候选切换，token 由 6.6k 升到 14.0k。

**回归测试**：`tests/test_content_gate.py`（当时文件名是 `test_false_success.py`，31 项断言，含真实故障产物 `temp/fixture_print_fragment.jsp` 与正确对照 `temp/fixture_good_standard.pdf`）。其中一条断言专门记录"旧判据为什么拦不住它"：那份片段的名称匹配是通过的。

**遗留**：被校验拒绝的产物不会自动删除，会留在 `downloads/` 里（本轮留下 `downfile.jsp` 与 #6 第一次候选下错的 `89d65074….pdf`）——**已在第 32 节解决**。

### 32. 被拒产物自动移出下载目录

**背景**：校验判失败只是"不采用"，文件本身一直躺在下载目录里。连续三轮都留下了残渣——r15/r16 的 `89d65074f9244a58933fa3cb2a619f7b.pdf`（#6 第一次候选下错的济建建管字〔2020〕48号）、r17 的 `downfile.jsp`（#5 那件片段）。多轮回归之后，下载目录里就分不清哪些是有效结果、哪些是被拒的垃圾。

**改动**

1. `download.py` 新增 `quarantine_artifact(path, reason, download_dir)`：把被拒文件移到 `<download_dir>/_rejected/`，并在旁边写同名 `.reason.txt`（记录请求名称、来源页面、决策动作与全部拒绝原因）。重名不覆盖——同一份下错的文件在多轮里会反复出现，第二次起带内容摘要后缀（`downfile__8fd56fc5.jsp`）。
2. `graph.py` 新增 `quarantine` 节点，接在 `verify` 之后：`verify.ok` 为真才去 `report`，否则先移出下载目录，再按 `after_quarantine` 决定换候选还是收工。同时把 `downloaded_path` 置空（不再指向被拒文件），去向写进 `verification.metadata.quarantined_to`、`errors` 与 trace。
3. `download_direct` 中途失败（网络中断、超过体积上限）不再留下半截文件。

**r18 实测（downloads 清空后重跑）**：下载目录里**只剩 8 个被采用的结果**，两件被拒产物全部落到 `_rejected/`：

```text
downloads/                     8 个结果文件，零残渣
downloads/_rejected/downfile.jsp                      + .reason.txt（708 字节）
downloads/_rejected/89d65074f9244a58933fa3cb2a619f7b.pdf + .reason.txt（435 字节）
```

同一批 **8/9 成功（官方原件 3 + 网页导出 5）| 墙钟 144.2 秒 | 73.2k token**。

> 用法提醒：以后遍历 `downloads/` 收集结果时要排除 `_rejected/` 子目录。
> 另外这一轮顺带取得两个附带结论：① 图内重搜首次在真实环境下被触发（#4 第一轮检索 10 条但全部低于门槛 → 换更简单的检索词重搜 → 命中）；② #9 本轮拿到的是 75 页扫描件而非 140 页正式版——原因是上海住建委页面 `Page.goto` 30 秒超时触发候选切换，与本节改动无关；那件扫描件的文本层不可读，名称校验按既有规则跳过（第 28 节的已知取舍）。

**回归测试**：`test_rejected_cleanup.py`（25 项断言：单元行为 + 状态图端到端 + 半截文件清理）。

### 33. 按表全量爬取与结果汇总（sheet_crawl + report）

真实业务输入是一份编制依据汇总表：**424 行 × 3 列**（`规范/文件名称` | `标准号/文号` | `备注`），需要逐条到官网取文件，最后把结果汇总回表供人工复核。为此新增两个模块：

**`sheet_crawl.py` —— 从表里取任务并驱动批量**

```powershell
python -m standards_crawler_agent.sheet_crawl --list-types          # 先看文种分类与抽样预览
python -m standards_crawler_agent.sheet_crawl --spread --limit 12 --jobs 3   # 按文种轮转抽样的试点
python -m standards_crawler_agent.sheet_crawl --start 2 --end 107 --jobs 5 --timeout 120

```

选行参数叠加顺序：`--rows` → `--remark` → `--start/--end` → `--spread/--limit`。行号是 **Excel 显示的行号**（表头占第 1 行，数据从第 2 行开始）。`--spread` 按文号把行分成 国家标准/建工行业标准/地标/交通/法律/行政法规/部令/省市文件…等类别后**每类轮流取一条**，试点时才不会一屏全是法律。

**分块驱动**：424 行切成 4 块顺序跑（`temp/run_sheet_full.py`），每块 106 行、各自一份 `batch_summary.json`。好处是中断后从下一块接续，且中途就能先导一版 Excel 看分布。

**`report.py` —— 把结果汇总回表**


### 34. 内容实质校验：产物里到底有没有文件正文

**背景**：对 `downloads/` 全部 174 个 PDF 做内容审计后发现 **30 个产物只有文件名、没有内容**——正文完全不是目标文件，而是浏览器把网站页面打印成的 PDF。它们**全部记为成功**，而且已经被重命名成 `名称_编号.pdf`，磁盘上从外观分辨不出。典型的是用户点出的两个：

| 产物 | 实际内容 |
| --- | --- |
| `涂覆涂料前钢材表面处理…第1部分…_GB／T 8923.1-2011.pdf` | std.samr.gov.cn 的标准**著录页**；页面上自己写着"该标准采用了 ISO、IEC 等国际国外组织的标准，由于涉及版权保护问题，本系统暂不提供在线阅读服务" |
| `混凝土结构施工图平面整体表示方法制图规则和构造详图-现浇混凝土框架、剪力墙、梁、板_22G101-1.pdf` | doc88.com 的**付费阅读器外壳**："还剩 230 页未读，是否继续阅读？请拖动滑块继续阅读" |

30 个按实际内容分成 7 类：国家标准平台著录页 11、交通部标准平台著录页 6、doc88 付费外壳 3、ndls.org.cn「到馆阅读」著录页 5、商业标准站页 2（其一只有 20 字："使用微信扫一扫登录「电子标准网」"）、政府页面无正文 2、与目标完全无关的企业营销软文 1。

> **本节有一处结论后来被更正**：这里把 30 件一律叙述成"平台不提供全文／拿不到"，是**错的**。
> 逐件核对后发现其中 **12 件页面上就有通往正文的入口**（6 个交通部页面有「在线阅读」、
> 5 个国家标准平台页面有「在线预览 + 下载标准」、1 个有「在线阅读 + 在线预览」），
> 属于"有入口但没走通"，不是"平台不提供"。真正死因是状态图的一个缺陷，见 **第 35 节**。
> 本节其余部分（判据、门禁、清理）不受影响——这 30 个产物确实都不含目标文件正文。

**根因：三层全漏**

1. **唯一的内容校验只查标题，从不查正文。** `check_name_match()` 的判据是"请求名称的名称片段命中率 ≥60% 或字符覆盖率 ≥85%"，而标准著录页与文库外壳页**恰恰完整印着目标文件的全名**（这是它们的立身之本）。实测 GB/T 8923.1-2011 那条：`名称片段命中 1/2，字符覆盖 100%` → 通过；`looks_readable_text()` 也没拦住（该页有 1325 个通顺汉字）。代码里没有任何一处判断"这份 PDF 里是否存在文件正文"。
2. **通过校验后立刻改名，网页出处被抹掉。** 原始的 `page_export_<pid>.pdf` 是唯一的"我是网页导出"线索，`verify` 节点在 `ok=True` 时按规范名重命名，改完就没了。
3. **网页导出是"所有真实下载路径都失败"之后的自动兜底。** `reassess_download` 把模型重复选择的失败动作推进 `fallback_actions` 的下一项，而模型给的兜底链末端就是 `save_page_pdf`。GB/T 8923.1-2011 的真实链路是：`click_view_original` 失败 → `click_download` 失败（该平台本就不提供在线阅读）→ 又选 `click_download` 被"重复动作"逻辑拦下、强制改判 `save_page_pdf` → 导出著录页 → 校验通过 → 改名 → `success_page_export`。**"下不到"被系统性地转换成了"成功"。**

另有一处独立的候选层缺陷：`doc88.com` 在 `official_score` 上被扣到 0.0，但靠逐字相同的标题把 `page_score` 拿满，最终 `0.5×0 + 0.5×1.0 = 0.50` 仍然越过 0.35 的候选门槛——低信任域名只是"降权"而不是"拒绝"。

**修法：判据集中到新模块 `content.py`**

新增 `content.py` 作为"一份产物里到底有没有目标文件的正文"的**唯一判据来源**，`download.py`（校验落盘产物）与 `browser.py`（导出网页之前识别"本页没有全文"）共用，避免两处各说各话。判据顺序不能颠倒：

1. **否定证据**（优先级最高，`page_without_fulltext()`）
   - 平台自认没有全文：「暂不提供在线阅读服务」「不提供在线阅读」「仅提供在线阅读服务」「仅提供在线预览」「到馆阅读/到馆提醒」
   - 文库付费外壳：「还剩 N 页未读」「请拖动滑块继续阅读」「不看了，直接下载」
   - 登录/注册墙：「使用微信扫一扫登录」「扫码登录」「登录/注册后即可查看」
2. **肯定证据**（`document_body_evidence()`）：条款（第X条 ≥3）、章节、目次、前言、附录、规范性引用文件、编号条款（≥5）、编号条目（"一、"≥3）。
   其中**只有前六项算"正式文档"**——营销软文也用"一、二、三"分节，不能靠它证明文件正文存在。
3. **无任何证据且篇幅极小**：≤3 页且 <2500 字。
4. **标准著录页**：命中 ≥2 个著录字段（标准号/中文名称/英文名称/分类号/归口部门/标准状态/发布实施日期）且无正文结构。
5. **商业外壳**：命中 ≥3 个营销标识（企业主体、主营/进店/真实性核验、导读/推荐文章、上传于/粉丝量/下载积分、正版标准代购服务、付费墙）**且没有正式文档结构**——阈值取 3 是为了不误伤政府页脚里那句"技术支持：某某有限公司"（只有 1 处命中）。

**`notes` 与 `warnings` 分开**：`Verification` 新增 `notes` 字段承载**非致命观察**。扫描件（页数 ≥5、文本层几乎为空、页面以图像承载）进 `notes` 并标 `metadata.scan_only=true`——原始内容是存在的，不该判失败，但也不能假装文本比对跑过了。

**配套改动**

- **观察阶段提前判定**：`summarize_html()` 新增 `no_fulltext` 字段（含可写进 `reason` 的证据），`llm_planner` 提示词明确"出现 `no_fulltext` 必须选 `no_download`，不要选 `save_page_pdf`/`click_print`"，并强调"判断页面正文是否就是目标内容看的是**正文结构**，不是页面标题"。省掉一次无用的导出与一轮决策。
- **低信任域名硬拒绝**：`ranking.is_low_trust_domain()`，在 `graph.rank` 里于排序前剔除（并把剔除数量与域名写进 trace 与 `errors`）。第三方文库/内容农场/电商站永远不会托管官方原件，留它们在候选池里只会把任务引向付费外壳。
- **状态语义新增 `success_scanned`**：扫描件单列一格，`report.py` 有独立标签（"成功（扫描件，无文本层）"）与配色，批量汇总按 `成功 N/M（官方原件 X，网页导出 Y，扫描件 Z）` 分项。`success_scanned` 与 `success_page_export` 一起在「问题清单」里标为需人工复核。
- **`not_downloadable` 的新含义**：产物里没有文件正文时不再落到 `needs_confirmation`——"这里拿不到该文件"和"需要人去确认一下"是两件事。
- **`metadata.source_kind`**：产物性质（`original_file` / `page_export` / `scanned_document`）写进元数据，事后再有污染可以按来源筛出来，而不是只能看状态。

**不拆 `save_page_pdf`（有意为之）**

法律、行政法规、地方规章在很多官网上**就是 HTML 正文形态**（`中华人民共和国突发事件应对法`、`生产安全事故应急条例`、`山东省房屋建筑和市政工程质量监督管理办法`……），官网不提供 PDF 原件。拆掉"失败→导出网页"这条路会让这些任务全部失败，所以该路径保留；有了正文实质校验，"失败→导出网页"会自动变成：合法法条页（有条款/章节结构）→ 通过，著录页/付费壳 → 判失败。

新增 `tests/verify_snapshot.py` + `tests/diff_snapshots.py`：对 `downloads/` 每个产物跑一次 `verify_file` 并落盘快照，改动前后各跑一次做差集（只比较两侧都存在的文件——`downloads/` 是活目录，批次运行期间会增删文件）。结果：

### 35. 更正：这 12 件不是"下不到"，是状态图没跟到最后那一页

**起因**：用户看了产物后指出——《钢丝绳铝合金压制接头》GB/T 6946-2008 在标准平台上是**有下载入口的**，只是要先点侧栏的『查看文本』，它会在新窗口打开另一个页面，那一页才有下载按钮。

**复核结果：用户是对的，而且不止它一个。** 逐件核对 30 个空壳件的页面内容（脚本 `_audit_tmp/check_entries.py`）：

| 归类 | 件数 | 说明 |
| --- | ---: | --- |
| 平台声明拿不到（暂不提供在线阅读服务 / 到馆阅读 / 文库付费外壳 / 扫码登录墙） | 14 | 确实拿不到 |
| **页面上有通往正文的入口** | **12** | **属于"有入口但没走通"** |
| 页面上没有任何入口（政府页无正文 / 商业页 / 营销软文） | 4 | 另属别的原因 |

12 件里 6 件是交通部 `jtst.mot.gov.cn` 的「在线阅读」，5 件是标准平台 `std.samr.gov.cn` 的「在线预览 + 下载标准」，1 件是 GB 24543-2009 的「在线阅读 + 在线预览」。

**死因：`after_download` 的动作名白名单**

GB/T 8923.1-2011 的真实轨迹（`results/batch_sheet_full_03/15_…/result.json`）：

```text
choose    action=click_download  selector=text=查看文本      ← 按钮找到了，也点了
download  action=click_download  path=None
          navigated_to=https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=6BC8…   ← 新窗口确实开了
reassess  action=save_page_pdf   reason=模型重复选择已失败动作，已阻止重复尝试；无未尝试策略时停止
download  action=save_page_pdf   path=downloads\page_export_36140.pdf
```

也就是说：**按钮找到了、点下去了、新页面也开出来了，但那一页从来没有被看一眼。** 原因是 `after_download` 只把三种动作送回 `observe`：

```python
if plan.action in {"click_view_original", "follow_attachment_page", "site_search"}:
    return "observe"
if plan and attempts < limit:
    return "reassess_download"     # ← click_download 落到这里
```

`reassess_download` 用的是**旧页面**的观察结果，模型看到「查看文本」还在，又选了一次 `click_download`，被"重复动作"逻辑拦下，只好走 `fallback_actions` 末端 —— 也就是 `save_page_pdf`。

**同一网站、同一个按钮，成败只取决于模型给点击贴的动作标签。** 12 件里唯一走通到第二跳的是《生产过程安全卫生要求总则》：

```text
choose    action=click_view_original  selector=text=查看文本   ← 只因为它被标成了 click_view_original
download  ... navigated_to=…/newGbInfo?hcno=37E7…
observe   url=…/newGbInfo?hcno=37E7…                          ← 走进了白名单，重新观察了！
choose    action=click_download  selector=text=下载标准         ← 在新页面上立刻找到下载按钮
download  ... navigated_to=…/showGb?type=download&hcno=37E7…    ← 一路点到真正的文件端点
reassess  action=save_page_pdf                                 ← 第三跳又死在同一个地方
```

标成 `click_view_original` 的进了白名单、跟到了新页面并找到「下载标准」；标成 `click_download` 的 7 例全部断在第二跳。**这不是"有的站点难有的容易"，是同一个按钮有一半概率走对。**

**四处修改**

1. **`after_download` 改判据**：由"动作名是否在白名单"改成"**当前地址是否还是刚观察过的那个地址**"。跳转/弹窗本身就是信号，枚举动作名必然漏——这次漏的恰好是最容易弹窗的 `click_download`。
2. **「仅提供在线阅读服务」≠「没有全文」**（上一轮已改）：前者是"能在线读、只是不给下载"，正确做法是点开阅读入口。把它判成"拿不到"会让判据**挡住正确的路**（GB 24543-2009 就是被它挡的）。现在拆成 `no_fulltext`（确实没有）与 `online_reading_only`/`reading_entry`（正文在入口后面）。
3. **弹窗不关掉，交给下一轮观察**：`browser._handoff()` 把刚打开的窗口连同渲染结果一起交给 `observe`（复用已有的 `pending_observation` + `_live_page` 机制，与站内检索"原地渲染结果"完全一致），而不是像以前那样 `popup.close()` 只留一个地址。理由：阅读器页常靠 JS + token 渲染，重新打开同一 URL 可能看到空白。顺带修掉一处：点击后**原地导航到 HTML**（阅读器/预览页）时不再把响应体当文件落盘——那只会得到一份"无法识别文件类型"的产物、白占一个候选。
4. **有入口时不许把当前页拍成 PDF**：`graph.redirect_page_export()`。模型想 `save_page_pdf`/`click_print` 而页面上还有入口、且**能断定这一页本身不是正文页**（`content.page_is_not_a_document`，用大 `page_count` 调用以免"篇幅小"误伤）时，改成去点优先级最高的入口（`下载标准 > 查看文本 > 在线阅读 > 在线预览`）；入口已试过就如实判 `no_download`。官网 HTML 正文的法律法规页因为本身含条款结构，不受这条影响。

**验证**（`tests/test_content_gate.py` 135 项断言，全部离线）

- 新增**三跳重放**：假浏览器复刻"记录页 → 点入口 → 阅读页 → 点下载 → 文件端点（导航被 Playwright 转成下载，observe 回报 `direct_file`）→ download_direct"，断言三跳都被观察到、动作序列为 `click_download → click_download → download_direct`、最终拿到文件且**没有退化成网页导出**。
- 新增 `newest_popup()` 单元测试（挑最后打开的窗口、关掉多余弹窗、忽略同址窗口）、`prefer_reading_entry()` 优先级、`redirect_page_export()` 三种分支、`page_is_not_a_document` 正反例。
- 快照复跑：**151 件里 ok 数不变，零翻转**——这两轮改动没有影响任何此前通过的产物。

**遗留（未做，留待真实批量验证后再决定）**

- 这 12 件的入口可达性**没有做端到端联网复验**；上面第 3 跳的 `showGb?type=download` 是否真能给到 PDF，是按 `observe` 的 `direct_file` 分支与站点 URL 形态推断的。
- **按钮发现的盲区**（观察到"看得见的都点了"，但不能证明"没有看不见的"，以下是读代码所得）：`javascript:` 开头的 `<a>` 被 `_collect_links` 整个丢弃；`_collect_buttons` 只看 `button/input/[role=button]`，DOM 兜底要求 class 含 `btn|button` 或带 `onclick` **属性**、标签 ≤24 字、总数 ≤30；零尺寸/移出视口的元素被可见性过滤剔除；不穿透 `iframe` 内部文档；`_open` 只等"正文 >200 字"和链接数稳定，**不等按钮渲染**。这些都还没动——上一轮的教训正是"凭推测加判据"。

### 36. 页面声明的身份：在下载之前就认出"这不是目标文件"

**起因**：第 35 节那轮真实批量（12 个"页面上有入口"的任务）跑出 **10/12 成功、拍网页动作从 12 次降到 1 次**，但逐份核对内容时发现 `坠落防护安全绳` **下成了《坠落防护 安全带》**（GB 6095-2021），而且记为 `success`。

**为什么没拦住——三道防线全在这一个案子上失效：**

1. 候选选错：排第一的是 `newGbInfo?hcno=DFB116…`，页面标题 `国家标准|GB 6095-2021`。两个标准名只差最后一个字。
2. **名称校验被跳过**：那份 PDF 的文本层是字体子集乱码（`犌犅 ６０９５ — ２０２１`），`looks_readable_text` 判为不可读 → `check_name_match` 直接返回"跳过名称校验"。查证发现**匹配器本身是判对的**（字符覆盖 86% < 90% 门槛、片段 0/1），只是没跑。
3. 第 34 节的正文实质校验也不命中：22 页 > 3，"篇幅小"不生效；乱码里既没有条款结构、也没有"无全文"声明/著录字段/商业特征。

量化第 2 条：这轮 12 个产物里有 **5 个文本层不可读**（3 个真扫描件 + 2 个乱码）。那道"不可读就跳过"的开关，**在最需要校验的多数产物上等于把校验关掉了**；而把开关强行打开又会错杀 2 个正确文件（覆盖率 0%，因为文本层是乱的）。

**关键观察：校验机制没错，是校验对象错了。** 候选页的 HTML 元数据是可读的，而且明写了标准号与正式名称：

```text
（安全带页）标准号：GB 6095-2021      中文标准名称： 坠落防护 安全带
（安全绳页）标准号：GB 24543-2009 采  中文标准名称： 坠落防护 安全绳
```

拿这两个值和请求名一比，同一套阈值就能把 86% 与 100% 分开。

**做法：`content.declared_identity()` + `content.compare_declared_identity()`，在 `graph.observe` 里调用**

候选页只要出现「标准号：」或「中文标准名称：」字段，就先核对一次；不匹配就**清空观察结果**，`after_observe` 自动切下一个候选（不需要新增图分支）。没有这两个字段的页面（公文页、列表页、检索结果页）一律不干预——上线前拿 19 个真实候选页验证过，**只有 2 个带著录字段**，误杀面很小。

判据与 `check_name_match` 保持同一套容忍度，不新造一套：

| 场景 | 结果 |
| --- | --- |
| 《坠落防护 安全**带**》页 vs 请求"安全**绳**" | 拒绝（字符覆盖 86% < 90%） |
| 《高层民用建筑钢结构技术**规程**》vs 请求"技术**规范**" | 放行（92%，文种词差异） |
| 页面《混凝土结构**工程**施工质量验收规范》vs 请求少个"工程" | 放行（100%，漏字笔误） |
| 页面标准号与请求名里的标准号冲突 | 拒绝 |

**两个踩过的坑（都写进了测试）**

1. **不能直接复用 `check_name_match`。** 它的第一道闸门是 `looks_readable_text`（≥120 字、高频汉字占比 ≥1%），而"中文标准名称"字段只有十来个字，**永远过不了那道闸门**，于是它一律返回"跳过校验"——闸门等于没接上。上线前验证时先踩到一次（安全带那页被判成"通过"）。短字段要另写比较函数。
2. **纯子串判断太松。** `"坠落防护安全绳"` 是 `"坠落防护安全绳用连接器"` 的前缀，会被直接放行，而那是另一份标准。现在要求"多出来的那段必须是限定语"（`（附条文说明）`、`第1部分：钢直梯`、纯编号/标点/拉丁后缀），见 `QUALIFIER_SUFFIX`；既拦住"用连接器"，也不误杀"第1部分：钢直梯"这类正常长名字。

**同时迁移**：`extract_standard_number` / `normalize_standard_number` 从 `download.py` 迁到 `content.py`（新闸门要用，而 `download.py` 本就 import `content.py`，反向依赖会成环）。函数体一字未改，`graph.py` 改为从 `content` 取用。

### 37. `reading_entry` 只认真实可点的控件

**起因**：第 36 节那次真实重跑里，`坠落防护安全绳` 已经不再下错文件（自动跳过《安全带》候选、落到《安全绳》页），但链子断在下一跳：

```text
[observe] ok     …/showGb?type=online&hcno=B7C913…
[choose_download] click_download  sel=text=在线预览
   :: …该控件未在buttons中显式列出但属于reading_entry.entries，需点击进入全文页后才可下载
[download] err=无法点击下载控件（text=在线预览）：Locator.click: Timeout 8000ms exceeded.
          Call log: - waiting for locator("text=在线预览").first
```

**根因是我上一轮自己加的**：`reading_entry` 是从页面**文本**里正则认出来的，而「在线预览」这四个字还会出现在按钮标签之外的一堆地方——i18n 脚本、`本系统仅提供在线阅读服务` 那句话、隐藏模板。提示词又写着"出现 `reading_entry` 就选 `click_download`，selector 用里面的入口文字"，于是模型忠实地去点一个**页面上并不存在**的控件。

报错里那个 `.first` 是 `_locator()` 兜底分支的痕迹：`text=在线预览` 只剩隐藏匹配、没有一个可见的，于是退回 `locator.first`，`.click(timeout=8000)` 一直等它可见 → 白等 8 秒。

**另外把「在线预览」点不动的原因查清楚了**（免得以后重复调查）：

- 平台源码里那个点击处理**整段被注释掉了**：`//if(supported) { showGb(el.attr('data-value'),'online'); //} else { …`；
- `supported` 是一次 WebAssembly 能力检测，不通过时按 i18n 的 `previewMsg` 提示
  「当前浏览器暂不支持标准全文在线预览服务，请使用现代浏览器…」；
- 实测在无头 Chromium 里连点两次都报"点击成功"，但 **URL 一字未变、正文长度没变**——点了不做事；
- 而 `showGb?type=online&hcno=…` 会**弹回** `newGbInfo?hcno=…&refer=outter`，根本没有真正的阅读器页。

也就是说这是**平台侧的有意门控，不是我们漏了什么**，`not_downloadable` 是如实结论，也不该去绕过。

**做法**

- `content.clickable_reading_entries(entries, control_labels)`：入口标签与**真实控件标签**求交集，只保留交集内的。
- `browser.summarize_html()`：用 HTML 解析出的 `buttons` + `links` 标签做第一次过滤；被撤掉的字样写进 `instruction`，明确告诉模型"这些只是提示文案或脚本文本，不是可点击控件"。
- `browser.refine_reading_entry()`：在 `drop_hidden_controls()` **之后**再收一次（单独抽成函数，为的是让"可见性过滤之后"这一步能被离线测试直接调用）。此时 `entries` 为空且页面也没有"仅提供在线阅读"声明，就整段撤掉 `reading_entry`，不递一个点不到的选择器给模型。
- `llm_planner` 提示词相应收紧：**`entries` 为空时一律不要点**；`selector` 必须来自 `buttons`/`links` 里真实列出的控件。

**验证**

- `tests/test_content_gate.py` **163 项断言全过**（新增 L 段 14 项），用两段**真实页面结构**做样本：有 `button.ck_btn` 的著录页 → 保留「在线预览」、撤掉只出现在提示文案里的「在线阅读」；没有该控件的"弹回来"页 → `entries` 为空并明确告知找不到入口。
- 快照零回归：160 个可比产物判定完全不变。
- **真实重跑对比**（`results/batch_gate_check_01` vs `_02`）：

| | 修入口之前 | 修入口之后 |
| --- | ---: | ---: |
| 第二次 observe 后的决策 | `click_download text=在线预览` | **`no_download`** |
| 点击超时次数 | **1（8 秒）** | **0** |
| 节点耗时合计 | 32.2s | 18.6s |
| 大模型 token | 8,205 | 5,749 |

### 39. 头名词兜底页：判据、检索间隔、冷却重跑（A 项三件）

**起因（用户提出的现象）**：同一条检索词，有时返回正常结果，有时返回"按头名词硬凑"的一批推荐页——查《山东省建筑工程安全专项施工方案编制审查与专家论证办法》，回来的是**百度百科「山东 省」、山东省人民政府首页、山东旅游攻略、百度地图**（头名词就是「山东省」）。更麻烦的是这批结果**能过当时的闸门**：闸门算的是"去掉通用词后字符集合的重合度"，而这些页面零散覆盖了查询里若干常用字，重合约 0.4 → 判"相关" → 省政务门户首页进了候选池 → 状态图去观察这堆门户、再在其站内检索上来回试，几十次浏览器往返全白花，最后可能**把门户首页导出成交付件**（那正是"内容不对的假成功"）。

在动手之前，先把"到底是引擎的问题还是我们的问题"查清楚了（第 40 节的实验清单）：代码/检索词/解析时机、无头与真实 Edge UA、有头浏览器、cookies、隐身模式、locale、mkt、`site:`、并发 jobs 3 vs 1、我们自己的检索量（120 次 / 131 秒）——**全部排除**。留下的事实只有两条：① 同一条查询在分钟级窗口内**确定**地复现同一批兜底结果（9 分钟内 12/12）；② 窗口会自己开合（约 20~40 分钟），而且**同一秒里两条查询可以一条正常一条兜底**（因此不是 IP 级限流）。既然引擎的行为观测不到也控制不了，改动就只能放在我们自己这一侧：**认出它、别为它花钱、隔一个窗口再来一次**。

**A-1 兜底页判据（`search.fallback_signature`）**

判据：把查询（去掉引号与 `filetype:`/`site:`/`最新 现行`）与"标题+摘要+URL"**两侧都掐掉空白**后，看查询在结果里**连续出现**的最长长度。真命中里查询本来就是连续出现的；兜底页靠头名词最多只能拼出 3~4 个字（「山东 省」掐空白后是 3 个字）。门槛 `FALLBACK_MIN_RUN = 6`：真要卡到 20 字，被引擎截断的官方发布页（实测「山东省住房和城乡建设厅 行政规范性文件 山东省住房和城乡 ...」）会被误杀。判为兜底时整批不进候选池，判定记 `fallback`，与既有的 `no_match` 一样**立刻停止重读**（同窗口内重读实测 0 收益），原始批次照样写进 `trace.discarded_batches`。

- **第一版判据被数据否决**。第一版用"去掉通用词后的片段"当判据，理由是通用词会稀释辨识度。回放 2541 条历史批次后发现它**把真结果判死了 385 批**：「公路工程技术标准」去掉 工程/技术/标准 后只剩「公路」2 字，而门槛 3 字，连命中的正主（`交通运输部关于发布《公路工程技术标准》的公告`）都过不了；「住房和城乡建设部关于修改部分部门规章的决定」被剐成碎片后同样过不了。改成"原始查询连续比对"后这类误杀消失。教训与第 30 节同一条：**判据要在真实批次上回放，别在脑子里推演**。
- **留一个保守出口**：批次里有**权威站上的深层内容页**（`is_authoritative_domain` 且路径层级 ≥ 2）时不判兜底。这条出口是从数据里长出来的：兜底页能给的最多只有门户首页（`shandong.gov.cn/`、`jinan.gov.cn/`、`mot.gov.cn/`、`gov.cn/gwyzzjg/`），而被这一条救回来的真线索全部落在深层页上（`openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=…`、市场监管总局政策页、中国政府网政策页）。加上出口后，会被判兜底、但批次里含当时真正用之交付的那一页的批次从 237 降到 **63**。
- **取舍是清楚的**：判据只在一个方向上会出错（把真批次判成兜底 = 丢一批线索），所以门槛、掐空白、深层页出口全部取保守值；宁可漏判几批兜底页，也不误杀真结果。

**A-2 检索间隔随机化（`search.query_gap`）**

两次检索之间留 `3~5 秒随机`（`SEARCH_MIN_QUERY_INTERVAL=3`、`SEARCH_QUERY_JITTER=2`），刚判过兜底/无结果的下一次再多等 8 秒（`SEARCH_FALLBACK_BACKOFF=8`）。**必须说清楚把握到什么程度**：批处理里检索是串行连发的（实测 120 次 / 131 秒），人工检索不会这样；但"连发导致兜底页"这个机制**没有被证实**（同一秒内一条正常一条兜底、串行 jobs=1 也照样出现兜底页）。所以这三个数字是**礼貌间隔**，不是已证实的修复；代码注释里也是这么写的。

**A-3 冷却重跑（`temp/run_cooled_two_pass.py`）**

第一遍跑选定行 → 冷却 **20~30 分钟**（区间内一次性随机取定）→ **只重跑没成功的行** → 输出"一次命中 / 重跑命中 / 仍失败"对照表（`results/<pass2>/two_pass_report.json`）。依据：同查询在窗口内是确定的，原地重试毫无意义；而昨天相邻两块相隔约 25 分钟，229 行里恢复了 39 行。支持 `--rows` / `--rows-file` / `--names-file`（名称跨表稳定，行号会漂移）/ `--start --end`，`--dry-run` 先看选中了什么。脚本会打印**聚合检索速率**估算（`jobs ÷ (间隔+单次耗时)`）与实测连发参照值 0.92 次/秒，默认 `--jobs 2`（≈0.36 次/秒）——因为间隔是**每个进程各自**的，并发越高聚合速率越接近当年出现兜底页的那个状态。

**验证（回放 + 夹具 + 断言）**

`temp/fallback_calibrate.py` 把 `results/*/*/result.json` 里落盘的**全部历史检索批次**用新判据重跑一遍，并用"这批里含不含当时真正用之交付的 `source_url` 那一页"当"真命中"的客观标签（不是我看着像）：

| 指标 | 数值 |
| --- | ---: |
| 考察批次（旧闸门判相关的） | 2541 |
| 新判据判为兜底页 | 680（**26.8%**） |
| 真命中批次的字面连续命中分布 | min 2 / p10 3 / 中位 **10** / max 35 |
| 会被判兜底**且**含 `source_url` 的批次 | **63** |
| 其中当时状态本来就是失败（`not_downloadable` 45 + `needs_confirmation` 15） | 60 |
| 其中 `source_url` 是站点根/浅路径（门户首页类） | 60 / 63 |
| 成功族里被判兜底的 | **3**，三条都是 `http://www.shandong.gov.cn/`（**门户首页导出**，正是要治的假成功） |

- **回归夹具**（`tests/fixtures_fallback_pages.json`，由回放脚本自动生成，未经加工）：`现场复现` 1 条（用户看到的那批：百度百科「山东 省」+省人民政府首页+知乎旅游+百度地图）、`正例` 6 条（分属 6 个不同任务，头名词分别是 建筑/施工/关于/模板）、`反例` 8 条（含 `source_url` 且最长连续命中 10~20 字）。

**这一版没治的**：窗口本身。判据只让兜底窗口里的这一次别白花钱，窗口关着时那条查询就是拿不到结果——只能靠冷却重跑换窗口（A-3），或者换入口（站内检索/标准平台）。另外"连发是否加重兜底"仍未证实，A-2 只是把节奏调回人工检索的样子。


### 40. 「同一条检索词有时正常、有时返回兜底页」——排查记录与结论边界

用户问的是"是不是负载太高/被风控限流了"。这一节把**做过哪些实验、各自排除了什么、剩下什么**记下来（脚本在 `temp/probe_*.py`、`temp/serial_retry.py`、`temp/burst_experiment.py`、`temp/compare_serial.py`，产物落在 `results/probe_*`、`results/serial_retry_01`），因为"我们的问题"和"引擎的问题"对策完全不同，必须分清楚再动手。

**结论（可以先看这两条）**

1. **兜底页是"某条查询在某个时间窗里没有匹配"的确定性结果**：同一条查询在 9 分钟内 12/12 复现同一批无关结果；同一个窗口内换浏览器页面、清 cookies、重读 3 次都拿到同一批。
2. **窗口会自己开合，周期约 20~40 分钟**，且**不是 IP 级/账号级限流**：同一秒里两条不同的查询，可以一条返回正常结果、另一条返回兜底页。所以它更像是"这条查询在引擎侧的某个分片/缓存里此刻没有可用的精确匹配结果"。

**做过的实验（每一行都是一个反例，排除了一种解释）**

| 假设 | 实验 | 结果 |
| --- | --- | --- |
| 是我们的代码/解析时机问题 | 同查询连续读、换页面重读、加长等待 | 同一批结果，排除 |
| 是无头浏览器被识别 | 无头 / **真实 Edge UA** / 有头（真实窗口）三种模式对比 | 结果逐条一致，排除 |
| 是无头浏览器被识别（2026-09-16 复现） | 同窗口 A/B/A：无头 → 有头 → 无头 读同一条查询（`temp/probe_headless_vs_headed.py`） | 三次 URL 逐条相同（2 条查询 × 3 次），排除 |
| 是缺少 cookies/会话 | 带 cookies、全新隐身上下文两种情形对比 | 一致，排除 |
| 是 locale / mkt 参数 | `setlang`、`mkt=zh-CN`、`cc=cn` 组合 | 一致，排除 |
| 是查询语法 | `site:` 限定、加/去引号、`filetype:` | `site:` 被引擎忽略；引号形态不影响兜底与否，排除（**2026-09-16 部分更正：见下方"更正"与新第 41 节**） |
| 是我们的并发太高 | 同一批 13 行：`jobs=3` 并发 vs `jobs=1` 串行 | 串行 8/13、并发 5/13；串行同样出现兜底页，**不是并发导致**，但串行确实更好 |
| 是我们的检索量太大 | 131 秒里连发 120 条查询，前后对比同一批查询的返回 | 前后一致，**没有**随检索量恶化，排除 |
| 是瞬间被限流 | 同秒交替发"已知正常"与"已知兜底"两条查询，看是否互相影响 | 互不影响：一条好、一条坏，同时成立，排除 IP 级限流 |

**剩下的事实与不可观测的部分**：兜底页的召回依据是**头名词**（实测出现过「工程」「关于」「省」「山东省」），三种不同的检索词形态会塌缩成**完全同一批**结果（去重后约 10 条）——说明它根本不是"对这条查询的检索"，而是引擎侧的降级路径。这条降级路径何时触发，我们从外部**观测不到也控制不了**：不在我们的代码里，不能靠改参数修好。因此 A 项（第 39 节）做的是三件事：**认出来**（别让门户首页进候选池、别在站内检索上空转）、**别为它花钱**（同窗口不重读）、**换窗口再来**（冷却重跑）。

**这条记录存在的意义**：此前"兜底页"只在对话里被解释过，仓库里没有留下实验与结论边界，于是下次有人（或模型）再问"是不是限流"，只能从头猜一遍。现在要改 A 项的判据或间隔，先看这一节，别重复做已经做过的实验。

**"改成有头试试"不必再临时改代码**：有头/无头已经是一个开关（`BROWSER_HEADLESS=0` 或 `--headed`，见开头"有头 / 无头"一节；**默认无头**，因为有头弹窗会抢焦点影响正常工作），`temp/probe_headless_vs_headed.py` 也是现成的同窗口 A/B/A 脚本。2026-09-16 复现过一次：同一个任务在 13 分钟内以无头跑是兜底页、以有头跑拿到 26 条真结果——**差异来自窗口开合，不来自模式**（A/B/A 三次逐条相同），别把它当成"有头治好了检索"。


### 41. 让模型看得见权威分、把"拿到了却选错页面"的一类修掉、兜底页换一种问法

触发：用户在浏览器里手动对比发现——**直接打开程序生成的那条链接是无关结果，而在搜索框里去掉引号重搜就是对的**。这个观察最后牵出三处改动，其中第一处和"Bing"无关。

#### 41.1 先做四路对照，把"导航方式"和"引号形态"拆开

`temp/probe_bing_submit.py`：goto 拼 URL / 搜索框提交 × 带引号 / 裸词，同一批查询交叉跑两轮，共 56 次读取（`results/probe_bing_submit_*/probe.json`）。窗口关着时的典型一轮：

| 路 | 查询形态 | 结果 |
| --- | --- | --- |
| `goto` | `"建设工程质量检测管理条例"`（**程序一直这么发**） | ❌ 兜底页：中国建设银行-网上银行（最长命中 2 字，政府站 0 条） |
| `goto` | `建设工程质量检测管理条例`（裸词） | ✅ 住建部令第 57 号 + 《建设工程质量检测管理办法》，政府站 9 条 |
| 搜索框 | 带引号 | ✅ 与上一行同批 |
| 搜索框 | 裸词 | ❌ 兜底页：中国建设银行（与第 1 行同批） |

**更正第 40 节那一行"引号形态不影响兜底与否"**：至少在"窗口关着"的时候，同一条名称的两种形态**可以一条坏、一条好，而且同时成立**（同一分钟内）。第 40 节那次比较是在"窗口开着"时做的，所以看不出差别——这是该行结论的适用边界，不是它的反面。

同时要说清楚**没有**被证实的部分：56 次读取里只有 3 次兜底（`goto+引号` 2 次、`搜索框+裸词` 1 次），样本**不足以**断言哪条路更有害；搜索框那条路也不更好，只是**不同**（「全省有限空间作业安全专项整治方案」走搜索框返回的是浙江、安徽的同类文件）。所以不要把它当成"改用搜索框提交就好了"。

#### 41.2 真正的窟窿一：候选选择器把政府站换成了内容站，而它看不到权威分

按上面那条线索回看轨迹时发现，「济南市建筑施工高处作业吊篮安全管理暂行规定」的失败被记成"Bing 兜底页"，实际不是：

```
排序（确定性）第 1 名 = www.jinan.gov.cn   官方 0.80 / 相关 0.95 → 总分 0.875
模型选择器改选       = doc.xuehai.net     官方 0.20 / 相关 1.00 → 总分 0.600
模型理由             = "虽然域名属于其他，但其内容直接指向目标文件…"
```

全量审计（`temp/audit_chooser_overrides.py`，126 个有选择器记录的任务）：

| 改序方向 | 任务数 | 成功 |
| --- | --- | --- |
| 认同确定性顺序 | 88 | 36（41%） |
| 在同层级里改选 | 27 | **23（85%）** |
| 换到更低层级 | 11 | **6（55%）** |

**这张表否掉了一个看起来很顺手的改法**：本来打算"禁止选择器向下换层级"（提示词里早就写了这条规则，模型 12 次改序里 8 次违反）。但向下改选的成功率（55%）并不比不改（41%）低——`cgzf.sh.gov.cn` ← `www.gov.cn`、`www.fxxq.gov.cn` ← `www.gov.cn`、`njszgl.cn`、`ttbz.org.cn` 都是靠改选拿到的。**禁止它会退回 6 个成功案例，所以没做**。这一条记在这里，免得下次又有人顺手加上。

实际做的是两件小事：

1. **把提示词承诺的字段真的发出去**。提示词从第一版起就写着"每条包含 … official_score（来源权威分）"，而 `_candidate_payload` **从来没有这个字段**——模型被承诺了一个拿不到的数字，只能自己猜来源可信度，于是把"URL 以 .pdf 结尾"当成了权威证据（8 次失败改选里，理由几乎都是"URL 是 .pdf 直链 / 标题完全匹配"）。现在 payload 补上 `official_score`、`page_score`、`combined_score`，并在提示词里点明这两类数字的口径，同时写明**"URL 以 .pdf 结尾"本身不是权威证据**，要选 `其他` 域名必须给出页面证据。
2. **按实测补黑名单**。判据三条（`temp/audit_selected_domains.py`，扫 1117 份 `result.json`）：性质上是文库/内容站/建站托管/商城/问卷、**被选中过**、那些任务 **0 成功**、且**从未作为交付来源出现过**。收了 11 个，最贵的是 `www.soujianzhu.cn`（被选中 17 次、17 次都没拿到文件）。

黑名单这一步是靠"按任务状态拆开的验证"（`temp/verify_blacklist.py`）才敢合的：它把"成功任务的交付页"和"失败任务当时在看的页"分开算——`faiusr.com`（凡科建站托管）在按域名审计里是"0 交付"，但按状态拆开后发现**另一个子域**`26431875.s21i.faiusr.com` 成功交付过《岩棉薄抹灰外墙外保温系统材料》，于是撤掉。最终：**成功任务的交付页被挡在池外的 = 0 个**，失败任务里的垃圾页被挡掉 79 处（`soujianzhu.cn` 一家 44 处）。

#### 41.3 真正的窟窿二：第一轮检索词里**从来没有裸词**

第 2 条检索词原先是"核心名（截掉文种词、仍带引号）"——它和第 1 条只差一个后缀，**形态重复**。而裸词形态只在第 2 轮（`build_retry_queries`）用，第 2 轮的门槛又是 `research = not pages`（候选池**恰好为 0**）：吊篮那条池子里有 15 条、质量检测有 10 条，所以**裸词一次都没发过**——用户手搜用的那个形态，程序从来没试。

改动：`build_queries` 的第 2 条换成**裸词**，第一轮发出的 3 条**形态互不相同**（精确短语 / 裸词 / `filetype:pdf`），请求次数不变（仍是 3 条）。核心名与「最新 现行」退到第 4、5 位（`max_queries` 调大时才发），裸形态的核心名仍由第 2 轮使用，没有丢。

#### 41.4 兜底页之后：换"提交方式 + 引号形态"再问一次

原来的做法是"判兜底就立刻停，交给上层换入口"——依据是"重读同一 URL 0 收益"。这条依据仍然成立，但**重读同一个 URL** 和**换一种问法**是两件事：换路（`goto` ↔ 搜索框）或换形态（带引号 ↔ 裸词）都会变成**另一条查询**，而另一条查询有它自己的命中窗口。

所以 `BrowserSearch.search()` 现在在 `no_match` / `fallback` 之后追加一次 rescue：走搜索框、送 `toggle_quote_form(query)`（去引号，但保留 `filetype:pdf` 这类限定词），并把两次尝试都写进 `last_read["attempts"]`（带 `path: gotourl / searchbox` 与 `sent`），成功则记 `rescued_by: "searchbox"`。判定仍然只有一个 owner（`_judge`），两条路共用。

代价要写清楚：**每次兜底多一次首页导航 + 一次检索**（一条任务最多 3 条检索词 → 最多 3 次）；只在已经拿到兜底页时才发生，所以不会让正常路径变慢。

### 42. 「有头/无头」改变过一类结果：PDF 直链被内联渲染成空白页

第 40 节证明了"浏览器模式不改变搜索引擎返回什么"，但**它改变同一份 PDF 在本地怎么被呈现**。这一节记的是把默认改成有头之后引入、又修掉的一个回归。

**现象（2026-09-16，同一批 27 个任务，失败形态按完整 `errors` 统计，脚本 `temp/audit_failure_forms.py`）**

| 轮次 | 浏览器 | 「候选是 PDF 直链却判『页面几乎没有内容』」 | 「搜索被兜底页挡住」 |
| --- | --- | ---: | ---: |
| 第 1 轮 | 无头 | **0** | 20 |
| 第 2 轮 | 有头 | **13** | 6 |
| 第 3 轮 | 有头（另三处修复后） | **14** | 0 |

那 13~14 条全是**官方附件直链**：`www.jinan.gov.cn/attach/0/*.pdf`、`zfxxgk.ndrc.gov.cn/upload/images/*.pdf`、`bzh.scjgj.beijing.gov.cn/bzh/apifile/*.pdf`、`www.chinamine-safety.gov.cn/zfxxgk/*.pdf`……也就是说，**我们要的文件就在那条候选上，程序却当它是空页、跳过、最后报"下不到"**。

**根因（两条路给出两个不同结论）**

- 无头 Chromium 没有 PDF 阅读器：`page.goto("…​.pdf")` 变成"开始下载"并抛异常 → `_is_download_start` 接住 → 返回 `direct_file` → 模型可以 `download_direct`；
- 有头 Chromium 用内置阅读器**内联渲染**同一份 PDF：`goto` 成功，但页面上没有正文也没有链接 → 在 `graph.observe` 里被当成空白页 → `RuntimeError("页面几乎没有内容")` → 换下一个候选。

`direct_file` 这条路本身很成熟——历史 **252 个任务**用过它、**169 个成功**（`temp/audit_direct_file.py`），包括那条 `济南市…深基坑"坑中坑"` 的任务。所以问题不是这条路不行，而是**有头根本没走到这条路上**。

**修法**：把这件事实在两条路上说成同一句话。`browser._looks_like_blank_document_view(url, summary)` 认"文档扩展名 + 没有链接 + 正文 < 200 字"，命中就返回 `direct_file`（与无头下那个分支共用 `_direct_file_observation`）。判据只认空文档页——**真正的文档发布页一定带链接**，所以不会把可操作的信息丢掉（V 段有正反例断言）。

**验证**

- 离线断言 302 → **306 项全过**（V 段：判据的四个正反例 + 用假页面跑 `observe`，确认空 PDF 返回 `direct_file`、有正文有链接的文档页不受影响）。
- 真机：同一批 27 个任务重跑，**第 1 块 3/3 成功**（工程建筑标准强制性条文 `success`、深基坑"坑中坑" `success` 31 页、山东省工程建设标准化管理办法 `success_page_export`）——此前三轮这一块最好也只有 1/3，而且那两条正是死在 `www.jinan.gov.cn/attach/0/*.pdf` 上的。**样本只有 3 个任务、且当时兜底窗口开着，不能当结论**；该轮在第 2 块开始时被人工中止，产物在 `results/queue_sample30_04_docfix/`。要结论得把这 27 条跑完。

**教训（写给下次改模式的人）**："换有头/无头"不是外观开关：搜索引擎那一侧确实不受影响（第 40 节），但**本地把响应当"页面"还是当"文件"取决于浏览器有没有内置阅读器**。凡是依赖"导航会抛下载异常"的判据，在有头下都会静默失效。
